# Impulse — Аналитика участника: сертификация Agentic Coding и матрица компетенций Skill Passport

**Статус:** проект продуктовой/функциональной спецификации для интеграции в Sber-Platform
**Дата подготовки:** 23.10.2026
**Приоритет:** конкретное поведение и достоверность данных, а не декоративная визуализация.
**Основа:** предоставленные пользователем `Итоговая_методология.pdf` (24 стр.) и `AI_PDLC_матрица_компетенций.txt` (сформирован 23.10.2026); сверка архитектуры с существующими возможностями Sber-Platform.
**Приложение:** `competency_anchors.md` — подробные исходные поведенческие критерии и цифровые следы для каждой роли/уровня, без изобретённых определений.

> **Граница применения.** Первый документ описывает **внутреннюю сертификацию сотрудников** Agentic Coding L1. Impulse работает со студентами/участниками. Можно использовать методологическую модель навыков в аналитике и Skill Passport, но нельзя показывать, что студент получил **официальный L1 Сбера**, пока нет подтверждения полномочий выдачи, формальной применимости методологии к этому участнику и достоверного результата из авторизованного источника. В учебной среде используем «Соответствие профилю L1: учебная оценка», а не «L1 подтверждён», если корпоративное подтверждение отсутствует.

## 0. Термины и недопустимые отождествления

| Сущность | Что означает | Шкала | Источник / правило |
|---|---|---|---|
| **Грейд 5 / 6** | Позиция пользователя в игровом/продуктовом пути Impulse, если она официально определена платформой | собственная шкала продукта | **не является** автоматически кадровым грейдом Сбера или Agentic Coding L1 |
| **Agentic Coding L1** | Результат внутренней сертификации по **совокупному** целевому профилю навыков | сертификация L1; уровни L2 Power User и L3 AI Architect описаны как отдельные ступени, их процедуры в PDF не раскрыты | PDF §1–2, §7–10 |
| **Уровень компетенции** | Насколько проявлен конкретный навык | **1** теория, **2** средний, **3** продвинутый, **4** эксперт; «нет данных» — **не** уровень 0 | TXT §0, ролевые матрицы; PDF §4, §6 |
| **Целевой уровень** | Порог конкретной компетенции для конкретной профессиональной группы / версии | 1–4 либо отсутствует | PDF §4, TXT §1.9 / §2.9 / §3.9 |
| **Подтверждённый (current)** | Результат допустимых цифровых следов/проверенных доказательств для данной модели | число 1–4 или `null` | модель расчёта с версией, period, provenance |
| **Прогноз (projected)** | Возможное изменение от будущего курса / задачи / проверки | число 1–4 или `null` + статус «Прогноз» | отдельный контур; не повышает confirmed |
| **Цифровой след** | Наблюдаемое действие: отправка задания агенту, вызов tool/skill, обращение к md, запуск субагента и т. п. | event с контекстом и правом на зачёт | PDF §6; TXT приложение А |
| **Цифровой артефакт** | Выходной результат: код, спецификация, тест, PR | ссылка/evidence | **не равно** цифровому следу: PDF §1.3, TXT §0.1 |
| **Skill Passport Impulse** | Версионированный профиль компетенций с происхождением подтверждений | профили + credentials + evidence | на основе имеющегося модуля компетенций Impulse |

**Инварианты:** `grade != certification_level != competency_level`. Слово «Senior» в исходной матрице AI-навыков не является подтверждённым HR-статусом. Проход курса не равен появлению цифрового следа; клик, вход в кабинет, просмотр страницы, отправка несвязанного артефакта не повышают подтверждённый навык.

## 1. Информационная архитектура раздела «Аналитика»

### 1.1. Первый экран (desktop)

Первый viewport аналитики участника (сверху вниз):

1. Заголовок **«Моя аналитика»**, переключатель активной траектории/профессиональной группы (разработчик, аналитик, тестировщик — только если профиль применим), видимый оценочный период и отметка обновления данных.
2. **Блок A «Матрица компетенций» / «Skill Passport»** — главная визуальная доминанта: циклограмма (радар либо горизонтальные полосы), легенда `Подтверждено / Цель / Прогноз`, срезы `Технические / Практические / Гибкие`. Внутри `Agentic Coding` показывать **6 навыков**, даже если один из них для текущей роли имеет `target=null` или только учебный теоретический уровень.
3. **Блок B «Сертификация»** — статус **Agentic Coding L1**, реальный или учебный контур с явной маркировкой, `N из M обязательных навыков`, основной дефицит, следующий шаг, бейдж только при легитимном подтверждении.
4. Ниже — **динамика навыков**, источники evidence, курсы/практика/тестирование, сертификаты Bootcamp и проектов, переходы к заданиям, затем прежние KPI и воронка участника. Ничего из существующей аналитики Impulse нельзя бесследно заменить.

Не размещать грейд Impulse как заголовок матрицы Agentic Coding; он допускается отдельным бейджем со ссылкой «Как считается грейд» и независимым источником.

### 1.2. Мобильная версия

1. Заголовок, роль и freshness; 2. Компактный прогресс компетенций + кнопка «Все навыки»; 3. карточка сертификации; 4. **список навыков** вместо нечитаемой миниатюрной паутинки; 5. раскрывающиеся подробности evidence; 6. вторичная аналитика.

Все разделы должны читать данные из одной согласованной версии профиля; при неизвестных данных не рисовать `0%`.

### 1.3. Навигация и действия

- Нажатие на сектор циклограммы или строку навыка открывает `SkillDetail` (drawer desktop, bottom sheet/route mobile).
- Нажатие на статус L1 открывает `CertificationDetail` с причиной, основаниями, источниками и персональным маршрутом.
- «Пройти недостающий навык» открывает **конкретный курс или checkpoint**, а не просто главную Bootcamp.
- «Показать доказательства» открывает разрешённые summary-evidence (источник, уровень, дата, rule), не сырые промпты.
- «Все документы» открывает действующие и отозванные сертификаты в портфолио; курс и проект имеют **разные виды credentials**.

## 2. Блок A — «Матрица компетенций» (основа Skill Passport)

### 2.1. Что отображается обязательно

| Элемент | Точное поле/смысл | Правило |
|---|---|---|
| Профиль | «Agentic Coding · Разработчик» / «Аналитик» / «Тестировщик» | человек выбирает из **доступных** профилей; активный не означает официальную кадровую роль |
| Модель | `Методология / версия / дата действия` | версия матрицы фиксируется для оценочного периода |
| 6 осей | Prompting; Prompt Engineering; Context Management; Tools/MCP; Creating Skills; Agents Team | канонический список ниже |
| Для каждого навыка | Название, **фактический уровень**, **целевой уровень**, краткий смысл уровня, статус, дата подтверждения | если нет источника, `current=null` и «Недостаточно данных» |
| Срезы компетенций | AI-навыки Agentic Coding как тип `practical` (с digital traces), учебная теория как `knowledge`, мягкие навыки — только по собственному framework | нельзя подменять практику прохождением учебного курса |
| Легенда | Current/достигнутые уровни — зелёный/бирюзовый, Target — **жёлтый**, deficit — **красный**, Projected — пунктир; Unknown — нейтрально | форма и текст, а не только цвет |
| Дефицит | `max(target-current,0)` **только если** оба значения известны | неизвестный уровень не трактуется как 0 |
| Основание | Количество разрешённых цифровых проявлений, категория события, источник, последний refresh | количество **не превращать** в новый порог сверх действующей методологии |
| Практический результат | проверенный проект/личный вклад/согласованная отметка эксперта — если такое доказательство разрешено **этой** моделью | для корпоративного L1 используем его собственные правила цифровых следов |
| Рекомендация | точное название курса, задания, теста **и** критерий закрытия дефицита | course/test не автоматически присваивают L1 |
| История | изменение уровней и provenance по периодам/версиям | отзыв доказательства/новая версия не стирают историю |
| Срез SDD | отдельная секция «SDD · наблюдение» | **НЕ** входит в целевые метрики L1: TXT §0, §1.8/2.8/3.8 |

### 2.2. Канонические компетенции (ключи для API)

| key | Название в UI | Что оценивается |
|---|---|---|
| `prompting` | Постановка задач агенту | От простых обращений и постановки задач до воспроизводимых библиотек сценариев |
| `prompt_engineering` | Правила работы агента | Rules, plan mode, командные системные правила |
| `context_management` | Управление контекстом | От прикрепления файлов до структурированного контекста и командных стандартов |
| `tools_mcp` | Инструменты и MCP | Использование, создание и командное переиспользование tools |
| `creating_skills` | Skills агента | Использование, создание и переиспользование специализированных skills |
| `agents_team` | Субагенты и Agent Teams | Использование субагентов, параллельная координация, создание субагентов |

Примечание: поскольку TXT содержит технические `creating tools`/`creating skills`, UI должен сохранять оригинальные идентификаторы в метаданных, но не обязан показывать англоязычные технические ключи в основной карточке.

### 2.3. Единая шкала 1–4 и конкретные поведенческие точки

| Уровень | Отображение | Что подтверждает | Можно ли повысить L1 только курсом? |
|---|---|---|---|
| **1** | «Начальный · теория» | По TXT — курс «Введение в GigaCode»; теоретическая подготовка. Это **отдельное** учебное evidence. | **Нет**; PDF §1.2 исключает отдельную оценку теоретического L1 в действующей L1-матрице. |
| **2** | «Средний · применяет» | Наблюдаемое базовое действие **из конкретной компетенции и роли** (например, приложил файл, вызвал tool, использовал skill) | Нет, если не выполнено правило соответствующей цифровой модели |
| **3** | «Продвинутый · управляет» | Специфическое продвинутое действие (работа агентом в agent mode, структурирование контекста, создание skill/tool, параллельная координация) | Нет |
| **4** | «Эксперт · масштабирует» | Систематизация и передача практики/командные правила/повторное использование **в пределах описанного для данного навыка**; некоторые следы пока «в проработке» | Нет; без внедрённого правила/следа показывать «Не оценивается автоматически» |

**Важно:** это только названия шкалы. Критерии уровней 2/3/4 **не универсальны**. Они разнятся по шести навыкам и ролям, точные определения и события представлены в §3 и `competency_anchors.md`.

### 2.4. Дизайн строки / tooltip / detail конкретного навыка

На строке **«Управление контекстом»** показывать, например, если реально известен результат: «Подтверждено 2 / Цель 3 · Требуется проактивная подготовка контекста». Под ней: `[Показать подтверждение] [Как достичь уровня 3]`, статус «События GigaCode за период: данные обновлены ...». **Число 2 — пример UI, не данные конкретного участника.**

`SkillDetail` содержит в строгом порядке:

1. заголовок, роль, версия методологии и источник; 2. `current / target / projected` с подписями; 3. шкалу 1–4, каждый уровень по клику раскрывает **«наблюдаемое поведение / точные виды цифровых следов / пример»**; 4. фактические подтверждения и исключённые события с причиной; 5. требования, которых ещё нет; 6. ближайшее действие (курс/практика) и допустимый эффект; 7. историю за выбранный период; 8. условия переоценки/свежести.

**Требование:** если уровень 4 помечен «в проработке», UI не должен показывать кнопку «Подтвердить» без работающей методики.

### 2.5. Точные источники подтверждения (категории)

- `gigacode_ide_event`: `chat_window.*`, `completion.*`, `settings.*`; `gigacode_cli_event`: `cli.*`, `cli_*`.
- `ai_agent_telemetry`: `AI_PDLC_CORE_AGENT_DATALAKE_TELEMETRY` для ролевых сценариев аналитика/тестировщика.
- `metrics_mart`: `rep.lists__v_tdatahub_engin_prompt_metrics.*`, `rep.lists__v_tdatahub_cli_metrics.*`, с обновлением по upstream.
- `course_verified`: теория или обучающий результат, **не** заменяющий событие корпоративной сертификации.
- `project_verified`: принятый результат проекта Impulse — отдельный трек Skill Passport; учитывается в Agentic Coding L1 только при опубликованном правиле маппинга.
- `human_feedback`: человеческое экспертное подтверждение для других компетенций Impulse, но **не ручное присвоение Agentic Coding L1**.

Показывать пользователю `evidence_id`, безопасную категорию, признанный уровень, дату, reference на действие/проект, правило подтверждения и актуальность. В обычный интерфейс **не выводить полный текст промптов, секреты, закрытый код и содержимое корпоративных логов**.

## 3. Конкретные точки владения по каждому навыку и роли

Детальные признаки цифровых следов и примеры — **в `competency_anchors.md`, разделы 1–3**. Ниже компактная продуктовая формулировка, которую нужно показать в попапе «Что означает уровень».

### 3.1. Постановка задач агенту (`prompting`)

- **Уровень 1:** курс «Введение в GigaCode» (теория — отдельное поле).
- **Уровень 2:** разработчик использует подсказки AI-ассистента в коде; аналитик/тестировщик назначает задачу соответствующему агенту через поддержанный рабочий сценарий.
- **Уровень 3:** разработчик формулирует задачу в агентном режиме (`chat_window.message.agent.sent`, `cli.message.sent`); аналитик/тестировщик работает с агентом по задаче, уточняет/корректирует её, направляет на доработку или делает agent-mode вызов.
- **Уровень 4:** сотрудник систематизирует успешные промпты для повторного использования (`settings_ide.prompt_library.new_prompt`); для ряда ролевых способов подтверждения — «в проработке».

### 3.2. Правила работы агента (`prompt_engineering`)

- **Уровень 1:** знание основ промпт-инжиниринга / теоретический курс; для тестировщика и аналитика в TXT отмечен теоретический целевой пункт, однако **в PDF есть расхождение** (см. §7).
- **Уровень 2:** создаёт и применяет rules/ограничения в начале работы (`chat_window.rules.applied`, `cli.mdfile.appeal`).
- **Уровень 3:** использует plan mode, формирует и принимает план/ТЗ (`chat_window.plan.created`, `chat_window.plan.confirmed`, CLI plan counters).
- **Уровень 4:** поддерживает общекомандные правила и системные инструкции (`settings.rules.new_rule` и прочие `settings.rules.*`), с отмеченными в исходной матрице неполными CLI-индикаторами.

### 3.3. Управление контекстом (`context_management`)

- **Уровень 1:** изучил теоретические основы; практический цифровой профиль отдельно.
- **Уровень 2:** реактивно прикладывает нужные файлы/ссылки и контекст (`chat_window.message.attach_file`, `cli_chat_message_attach_file_count`).
- **Уровень 3:** заранее готовит структурированные `md`, rules, README и спецификации, применяет `/init`, переносит контекст между сессиями; важны **реальные обращения агента к файлам**, например `mdfile_appeal`, а не одно только открытие истории. Для разработчика TXT дополнительно указывает строгие условия `GIGACODE.md`; их надо сохранить в tooltip.
- **Уровень 4:** создаёт и обновляет **общий** контекстный слой команды, стандарты, шаблоны и управление актуальностью. Набор автоматических индикаторов ещё требует методологической зрелости.

### 3.4. Инструменты и MCP (`tools_mcp`)

- **Уровень 1:** теория/общие представления.
- **Уровень 2:** агент действительно вызывает разрешённый инструмент или MCP; фиксируются успешный tool-call и решение пользователя по доступу. **Не** засчитывать один только текст «я подключил MCP».
- **Уровень 3:** создаёт либо обновляет инструмент, который агент затем использует (`cli_mcp_tool_create_count`, подтверждённые обращения к новому tool).
- **Уровень 4:** формирует командную библиотеку инструментов — в исходной методологии индикаторы **«в проработке»**.

### 3.5. Создание и использование skills (`creating_skills`)

- **Уровень 1:** теория/понятие навыка агента.
- **Уровень 2:** запускает существующий skill в IDE/CLI (`chat_window.skill.invoked`, `cli.cli_answer_skill_call_count`).
- **Уровень 3:** создаёт и регистрирует собственный skill **или** проходит альтернативный критерий регулярного использования skill. TXT содержит правило «3 вызова в месяц», требования к версии инструмента и директории хранения. Привязать к **версии правила**, поскольку число цифровых проявлений в основной PDF на этапе запуска не нормируется (§6.6).
- **Уровень 4:** созданные skills востребованы и регулярно используются другими; **цифровое подтверждение в проработке**.

### 3.6. Субагенты и Agent Teams (`agents_team`)

- **Уровень 1:** базовое знакомство с субагентами.
- **Уровень 2:** использует встроенных субагентов для решения сложных задач (CLI `cli.message.answer.subagent_execution`).
- **Уровень 3:** запускает/координирует нескольких субагентов в параллельной работе (`agent.parallel.work`, `agent_parallel_work_count`); для разработчиков указано: событие собирается, но ещё может не передаваться в дашборд.
- **Уровень 4:** создаёт специализированных субагентов (`cli_subagent_create_count`), но реализация в исходнике **«в проработке»**.

### 3.7. SDD / OpenSpec (только дополнительная наблюдаемая компетенция)

Показывать её **отдельно от обязательных шести осей** в блоке «Дополнительные компетенции (мониторинг)», сохраняя описание для разработчика, аналитика и тестировщика из TXT §1.8, §2.8, §3.8. SDD **не входит в расчёт достижения Agentic Coding L1** по этому текстовому источнику. Не считать просмотр OpenSpec или наличие папки доказательством уровня, если правило требует PR, структуру delta/master spec либо другие конкретные артефакты.

## 4. Целевые уровни Agentic Coding L1 — по источникам, без подмены

### 4.1. Сопоставление целевых уровней

В ячейках приведены **целевые числовые уровни конкретных навыков** (не сертификаты L1 и не грейды сотрудника):

| Навык | Разработчик: PDF §4.2 | Тестировщик: PDF §4.3 | Аналитик: PDF §4.4 | Конфликт с TXT |
|---|---:|---:|---:|---|
| Prompting | 3 | 3 | 3 | нет для профиля middle |
| Prompt Engineering | 4 | **2** | **не указан** | TXT: для тестировщика и аналитика целевой теоретический уровень **1** |
| Context Management | 3 | 2 | 3 | TXT аналитика §2.4: детальный блок отмечает 2 как целевой, но §2.9 таблица — 3 |
| Tools/MCP | 2 | 2 | 2 | нет |
| Creating Skills | 3 | 2 | 2 | для разработчика уточнить версию критерия «3 вызова в месяц» |
| Agents Team | 2 | 2 | 2 | нет |

**Не сводить** «Prompt Engineering = 2/1» к среднему или произвольному числу. До утверждения действующей версии: правило сертификации на конфликтной оси имеет `unresolved=true`, при отсутствии подписанного published-definition для соответствующего периода итоговый статус `requires_methodology_resolution`; учебная визуализация показывает обе позиции с указанием источников, но **не меняет официальный статус**.

### 4.2. Дополнительные профили junior/middle/senior из TXT (не HR-грейды)

| Навык | Разработчик junior / middle / senior | Тестировщик junior / middle / senior | Аналитик junior / middle / senior |
|---|---|---|---|
| Prompting | 3 / 3 / 4 | 2 / 3 / 4 | 2 / 3 / 4 |
| Prompt Engineering | 3 / 4 / 4 | 1 / – / – | 1 / – / – |
| Context Management | 2 / 3 / 3 | 2 / 2 / 3 | 2 / 3 / 3 |
| Tools/MCP | 2 / 2 / 3 | 2 / 2 / 3 | 2 / 2 / 3 |
| Creating Skills | 2 / 3 / 4 | 2 / 2 / 3 | 2 / 2 / 3 |
| Agents Team | 1 / 2 / 3 | 1 / 2 / 3 | 1 / 2 / 3 |

`–` = отсутствует обязательное требование в соответствующей таблице, **не** уровень 0. Столбцы `junior/middle/senior` — названия **целевых профилей AI-навыков** исходной матрицы, не назначение пользователю кадровой должности, стажа или зарплатной категории.

### 4.3. Честное отображение достижения целевого профиля

Для корпоративного Agentic Coding L1 в авторизованном источнике используется **конъюнкция обязательных навыков** `forall skill in published_profile: observed_level >= target_level` с учётом **именно тех** правил наследования и компенсации, которые применимы к роли. Уровни без данных или с конфликтом нельзя подставлять как 0/1 и нельзя считать достаточными.

**Компенсаторное правило разработчика (PDF §6.5, TXT §3.9):** если подтверждены **не менее 2 из 4**: `Context Management >=3`, `Tools/MCP >=2`, `Creating Skills >=3`, `Agents Team >=2`, то для профиля middle в указанной матрице могут считаться достигнутыми `Prompting=3` и `Prompt Engineering=4`. Отобразить причину: «Уровень рассчитан по компенсаторному правилу», перечислить **конкретные** доказанные входные навыки и версии правил. **Не применять** к тестировщику, аналитику или автоматически к профилю senior.

Для UI-запроса «N из M навыков»: знаменатель `M` — **число обязательных требований в опубликованной, согласованной версии матрицы для роли**; SDD и факультативные компетенции исключены. Показать `выполнено`, `не достигнуто`, `недостаточно данных` и `ожидает методологического решения` раздельно.

### 4.4. Процент компетенций / готовности — не сертификат

В существующей аналитике Impulse readiness определён как взвешенное среднее `min(current_level / target_level,1)` по обязательным навыкам с `coverage` и версиями модели. Это **продуктовый индикатор**, а **не** правило присвоения корпоративного L1. Рядом обязательны значения `подтверждено/всего`, покрытие источниками и методология. Если обязательный current неизвестен, показывать `partial` + coverage или `Недостаточно данных`, а не искусственные «62% освоено».

## 5. Блок B — «Сертификация»

### 5.1. Карточка на главной аналитики

**Заголовок:** «Agentic Coding · сертификация L1»; подзаголовок **«Внутренняя сертификация сотрудников»** / **«Учебный профиль по методологии L1»** в зависимости от допустимого источника. Ниже:

1. **Статус** (см. §5.3), не один только красный/зелёный цвет.
2. Профессиональная группа, версия целевого профиля, дата периода и свежесть расчёта.
3. `Соответствуют целевому уровню: N из M` с учётом §4.3.
4. 1–3 основных **неподтверждённых/неизвестных** требования с current/target, например «Creating Skills: 2 → 3; нет допустимого цифрового следа уровня 3».
5. CTA: «Посмотреть требования», «Открыть персональный трек» или «Как подтвердить» по статусу.
6. При подтверждении — действующий **бейдж L1** и канал верификации, если он действительно предоставлен внешним провайдером. **Не обещать PDF-сертификат L1:** PDF прямо закрепляет **статус и цифровой бейдж**, а не обязательную выдачу сертификата-файла.

Если нет официального результата: **«Официальное подтверждение L1 не подключено»** и, отдельно, разрешённый **учебный прогноз** без эмблемы официальной сертификации.

### 5.2. Детали сертификации (drawer / отдельная вкладка)

Точное наполнение:

- **Область:** «Для кого действует» и `eligibility`: целевая аудитория / вне аудитории / не определено, с причиной. Наличие выбранной профессии само по себе недостаточно (PDF §5).
- **Результат:** статус, `effective_at`, источник решения и правило; дата последнего обновления.
- **Профиль требований:** таблица 6 навыков (для аналитика возможно 5 обязательных в PDF) `Навык — current — target — статус — цифровое подтверждение — источник — следующее действие`.
- **Бейдж:** отображать только `issued` действительного issuer; хранить verification reference. Для неподключённой корпоративной выдачи — нейтральная информационная карточка.
- **Траектория A:** автоматическая оценка по рабочим цифровым следам; при соответствии всем обязательным элементам — подтверждение **без дополнительных занятий**.
- **Траектория B:** если профиль достоверно не достигнут, показать персональные практические задания в GigaCode → ожидание обновления следов → повторный расчёт; тест в BootCamp **только при необходимости**, после практики.
- **Тестирование:** статус назначен/пройден/нет, дата, предмет, итог проверки **знаний**; положительный тест **сам по себе не выдаёт L1**.
- **Ограничения:** отсутствие данных, проблема с интеграцией, нет доступного правила, несовпадение источников, «в проработке».
- **Ревалидация:** 2027+ — отдельный полугодовой период повторного подтверждения, следующий период, обоснование и статус. История ранее подтверждённых периодов остаётся в аудите.

### 5.3. Состояния по PDF §8.9, обязательные для UI

| key UI | Название | Что показывать и какая кнопка |
|---|---|---|
| `outside_target_audience` | Вне целевой аудитории | Причина/период; без красного «не сдал»; следующий пересмотр ЦА |

### 5.4. Статусы иных сертификатов Impulse (не путать с Agentic Coding L1)

В отдельной карточке **«Документы Skill Passport»** показывать **сертификаты обучения** и **сертификаты за подтверждённую проектную практику** раздельно. Для каждого — `document_type`, название, issuer, версия программы, период, дата, статус (`issued/revoked/superseded/demo`), verification ID/ссылка только при реальном наличии, перечень подтверждённых навыков, связанный курс/проект. Это **предлагаемый продуктовый контракт Impulse** по уже существующему OpenSpec `rating-credentials`, а не требование PDF о внутреннем L1.

Сортировка по дате, фильтр по типу и действительности. Недействительные/демо нельзя отображать как действующие, а баллы и сертификаты не создаются на основании просмотра страницы.

## 6. Какие графики и аналитические показатели показывать

### 6.1. Матрица/циклограмма

- 6 осей навыков, каждую подписать русским названием; шкала **1–4**, рядом обозначить `current / target` цифрами.
- **Контуры:** текущий подтверждённый — зелёный/бирюзовый, целевой (опубликованная версия) — жёлтый, дефицит — красный, прогнозный — пунктир (только при существующем course/project mapping); легенда и цифры дублируют цвета.
- Недостающий результат показан с указанием точного условия: «Нужен вызов skill», «Нет цифрового следа Agent Team», а не расплывчатое «Прокачай AI».
- Смена роли меняет *модель и target*, но не переписывает подтверждённые evidence; все роли берутся из разрешённой выборки.
- «SDD» — соседний диагностический модуль, **не** седьмая обязательная ось.

### 6.2. Динамика и источники

- `За 30 / 90 / 180 дней`: история **подтверждённого** уровня по каждому навыку; нулевой рост — возможное нормальное состояние, неизвестное — отдельное.
- Точки графика должны содержать дату/источник `evidence`, правило и версию. Если источник пересчитан/отозван, отразить коррекцию.
- Отдельный фильтр `IDE / CLI / агентные события / учебные evidence / проектные evidence`, где источник доступен и разрешён.
- Результаты курсов/тестирования не смешивать с цифровыми следами Agentic Coding; прогресс обучения показывать отдельно от сертификационного профиля.

### 6.3. Метрики, которые действительно выводим

| Метрика | Формула или правило | Что показывать при неизвестных данных |
|---|---|---|
| Обязательные компетенции закрыты | `sum(verified_target_for_required) / count(required_skills)` | `N / M` + unknown отдельно |
| Подтверждённость источников | `required_skills_with_usable_evidence / required_skills` | без округления до успешного показателя |
| Готовность к роли Impulse | existing weighted role readiness, `min(current/target,1)` с весами/version | `partial/unknown`, coverage |
| Профиль Agentic Coding L1 | `all(required_skills_met)` **при известной eligibility, опубликованной версии и валидных evidence** | `not_connected`, `insufficient_data` или `methodology_unresolved` |
| Прирост навыка за период | `current_level(end)-current_level(start)` по одной и той же версионированной шкале | «Нельзя сравнить версии», если шкала изменилась без опубликованного mapping |
| Теория пройдена | verified course evidence: «Введение в GigaCode» | «Данных об обучении нет», не обязательно «Не пройдено» |
| Рекомендованные практики | открытые gaps → версии целей → допустимые шаги/связанные объекты | пустая причина, если нет опубликованного mapping |
| Сертификаты | count действующих проверяемых credentials по type/status | «Нет подтверждённых документов» либо «Источник недоступен» |

**Запрет:** единый процент «62% навыков» без явной опубликованной формулы и покрытия; внешний L1 не выводить из числа пройденных курсов, количества баллов Impulse или суммы уровней 1–4.

### 6.4. Свежесть и режимы обновления

По PDF §9.9: логи GigaCode обновляются **ежедневно**, логи агентов — **по пятницам**, статусы обучения — **понедельник и среда**, целевая аудитория — **ежемесячно**, информация о навыках — **ежедневно**. Это периодичности **описанного корпоративного контура**, не SLA доступных сейчас API Impulse; показывать их как `expected_refresh`, а реальную свежесть брать из integration snapshot.

Если событие появилось сегодня и профиль ещё не пересчитан, UI сообщает «Ожидается обновление»; не показывает как уже подтверждённый прогресс.

## 8. Контракты данных: что расширяем относительно текущего Sber-Platform

## 9. Поведение и edge cases, обязательные для реализации

1. **Пустой профиль:** рисуем 6 `unknown`-навыков с методологией, не 0/4 и не 0% готовности.
2. **Официальная сертификация недоступна:** учебная модель без корпоративного статуса и бейджа.
3. **Один навык проверен, остальные unknown:** `1 подтверждено / N требований`, итог `partial`, не «не прошёл L1».
4. **Тест сдан без следов:** «Знания подтверждены тестом», L1 всё ещё без изменения.
5. **Практика выполнена, след в очереди:** `awaiting_recalculation`, текущий уровень не меняется.
6. **Агент вызвал tool, но событие не входит в правила роли/версии:** показываем `excluded`, не повышаем уровень.
7. **Уровень 3 превышает цель 2:** achieved=true, вклад в readiness ограничен target, повышенное мастерство отображается отдельно.
8. **Разработчик закрыл компенсаторное правило:** показываем derived confirmation с четырьмя проверяемыми входами, не создаём несуществующих событий Prompting/PE.
9. **Тестировщик / Prompt Engineering спорное требование:** conflict, не автоматический официальный L1.
10. **Аналитик / CM спорный target:** показать PDF=3 и пометку о TXT=2 в detail; официальное решение только из published profile.
11. **SDD освоен:** в отдельной секции, не двигает достижение L1.
12. **Смена роли:** контуры target и правила меняются, evidence не теряется и не переносится без rule compatibility.
13. **Отзыв credential или evidence:** пересчёт + неизменяемая история причин.
14. **Начало 2027 полугодия:** активная ревалидация работает по новой временной версии, ранее подтверждённое сохраняется в истории, UI различает «в прошлом периоде» и «в текущем».
15. **Неработающий/задержанный источник:** последнее время подтверждения + «Не обновлено», никакого автоматического обнуления.
16. **Только touch/mobile:** все tooltip доступны кликом, таблица переходит в вертикальные строки.
17. **Курс Bootcamp отмечен вручную:** self-reported / pending, **не** verified L1, Skill Passport помечает источник отдельно.
18. **Ролевая матрица поменялась:** прошлые snapshots воспроизводимы, новые требования применяются по `effective_from`.
19. **Пользователь входит в две роли:** разные профили/цели, единые допустимые events с ролевыми условиями, не повышать навыки другой роли без маппинга.
20. **Грейд Impulse изменился:** не пересчитывать задним числом Agentic Coding L1.

## 10. Нефункциональные требования и визуальный контракт

- Следовать согласованному UI Impulse (dark navy, бирюзовые акценты, читаемые светлые подписи, единая боковая навигация). **Матрица первична;** графики не должны конкурировать с ней декоративными карточками.
- Композиция desktop: матрица 60–65% рабочей области, сертификация 35–40% (при доступной ширине); на tablet/mobile складывать вертикально.
- Факты vs прогнозы: отличать цветом, пунктиром, легендой и словами. Не добавлять анимированный прирост уровня до подтверждения.
- Читаемый radar требует список эквивалентных данных для screen reader. Легенда и текст в `aria-label`; мышь, клавиатура и touch доступны одинаково.
- `prefers-reduced-motion` отключает вращения/пульсации/сложные анимации. Поля с длинными русскими названиями переносятся без обрезания.
- Состояния: loading/skeleton, empty, partial, stale, unavailable, error, access denied, conflict — отдельные компоненты, без ложных zeros.
- Время source freshness, date и timezone указаны на каждом вычисленном срезе. `response snapshot` единый, API не склеивает значения из разных периодов молча.
- Не выдавать внешние корпоративные данные/метрики в логи frontend, error trackers или аналитику кликов.

## 11. Критерии приёмки (Given–When–Then)

1. **Given** подтверждённый `creating_skills` уровень 2 и цель 3, **When** открыт skill detail, **Then** показано, какое событие/правило подтверждает уровень 3, и конкретный permitted next step.
2. **Given** нет разрешённых следов, **When** открыт профиль, **Then** current=`null`/«Недостаточно данных», а не 0 и не «не умеет».
3. **Given** подтверждён курс, **When** открыта сертификация, **Then** сертификат курса/теория видны отдельно и L1 не присваивается автоматически.
4. **Given** сотрудник соответствует всем опубликованным обязательным требованиям и authoritatively certified, **When** UI получает verified decision, **Then** статус L1 и бейдж отображены с verification provenance.
5. **Given** нет интеграции InTra, **When** студент открывает аналитику, **Then** нет настоящего корпоративного бейджа или ложной выдачи L1.
6. **Given** конфликт tester PE=1/2, **When** пытаемся вычислить официальный L1 без authoritative rule version, **Then** расчёт не производится и показывается methodology conflict.
7. **Given** SDD подтверждён, **When** считаем L1, **Then** SDD не входит в denominator и не увеличивает сертификационный прогресс.
8. **Given** digital evidence отозвано, **When** backend перестраивает snapshot, **Then** current и статус пересчитаны; audit trail сохранён.
9. **Given** тестирование пройдено, но новые цифровые следы отсутствуют, **When** отображается результат, **Then** тест виден как проверка знаний, L1 не подтверждается.
10. **Given** разработчик имеет 2 из 4 разрешённых входных навыков для compensation, **When** применяется соответствующая действующая версия матрицы, **Then** Prompting=3 и PE=4 объясняются как derived (не прямой след).
11. **Given** роль аналитика, **When** открыт опубликованный PDF-профиль, **Then** Prompt Engineering не включается в пятёрку обязательных по умолчанию; сохраняется отдельно возможная учебная цель из TXT.
12. **Given** смена масштаба с desktop на 390px, **When** пользователь открывает каждый skill, **Then** описание уровней 1–4 и источников полностью читается, не требует hover.
13. **Given** график current=2/target=3, **When** нажато действие «Пройти курс», **Then** открывается точный курс/первый checkpoint и projected не становится current.
14. **Given** данные по разным источникам обновлялись в разные дни, **When** отображается профиль, **Then** пользователь видит freshness каждой категории и дату общего снимка.
15. **Given** новый оценочный период ревалидации, **When** открыта история, **Then** прошлое подтверждение остаётся видимым и не смешивается с текущей сертификацией.
