## Purpose

Определяет отзывчивость переключения разделов при работе с реальными API-данными без подмены их mock-проекциями.

## ADDED Requirements

### Requirement: Повторная навигация не ждёт одинаковый read повторно

Frontend SHALL сохранять успешные GET-ответы в памяти текущей пользовательской сессии на короткий ограниченный срок и объединять одновременные одинаковые запросы. Переход назад в недавно открытый раздел SHALL сразу использовать уже полученные реальные данные. Ошибки и ответы предыдущей авторизованной сессии SHALL NOT кэшироваться.

#### Scenario: Пользователь возвращается в раздел

- **WHEN** пользователь повторно открывает раздел в пределах окна свежести и данные не изменялись
- **THEN** интерфейс использует тот же успешный API-ответ без второго сетевого ожидания

#### Scenario: Два виджета одновременно читают один ресурс

- **WHEN** два смонтированных виджета одновременно запрашивают одинаковый GET path
- **THEN** выполняется один сетевой запрос, а оба потребителя получают его результат

### Requirement: Изменение данных немедленно инвалидирует read cache

Любой изменяющий HTTP-запрос SHALL инвалидировать session read cache до отправки, чтобы ответ параллельного старого GET не мог восстановить устаревшее значение. Следующий read SHALL получать данные из API.

#### Scenario: Mutation выполнена между двумя чтениями

- **WHEN** пользователь изменяет доменный объект через POST, PUT, PATCH или DELETE
- **THEN** последующий GET выполняется заново и отображает состояние после mutation

### Requirement: Кэш ограничен сессией и временем

Read cache SHALL быть только in-memory, иметь конечный TTL и очищаться при login, logout и смене роли как при изменяющих запросах. Явный `Cache-Control: no-cache` SHALL обходить повторное использование. Persisted browser storage для API payload SHALL NOT использоваться.

#### Scenario: Требуется принудительное обновление

- **WHEN** запрос передан с `Cache-Control: no-cache`
- **THEN** frontend обращается к реальному API независимо от существующей cached записи

### Requirement: Оперативные данные не задерживаются read cache

Realtime reads сообщений и уведомлений SHALL обходить session read cache. Стандартные режимы request cache `no-store` и `reload` SHALL также принудительно обращаться к API.

#### Scenario: Приходит уведомление другого пользователя

- **WHEN** frontend повторно читает сообщения или уведомления
- **THEN** он обращается к API и не возвращает сохранённый ответ предыдущего чтения
