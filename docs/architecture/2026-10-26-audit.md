## ARCH-P1 — доказанное нарушение dependency direction

В 20 application и 10 infrastructure Python modules есть `from impulse.api.errors import ApiError`. Дополнительно `src/impulse/infrastructure/development_store.py:20` импортирует `impulse.bootstrap.ai_curriculum_details`. Это 31 импорт, нарушающий целевой layering contract.

- **Причина**: application/repositories и composition root имеют обратную зависимость от HTTP/конфигурационных модулей.
- **Риск**: сложнее изолированно тестировать бизнес-логику, менять transport, повторно использовать use cases, исключать побочные эффекты импорта.
- **Исправление**: внутренние transport-neutral ошибки и config ports; mapping `ApiError` в API, перенос imports по одному контексту и строгое сохранение codes/statuses/404 privacy/409 conflicts.
- **Безопасность**: это архитектурная задолженность P1, **не подтверждённый P0 security incident**.
- **Приёмка**: ноль неразрешённых layer violations; хотя бы idempotency, compensation, RBAC, API error-response characterization tests на каждой волне.

Полный построчный список находится в artifact `architecture.md` и машиночитаемом `architecture.json`. Временные исключения перечислены в `scripts/architecture/legacy-imports.json`, каждое с владельцем и датой истечения. Architecture CI теперь проверяет **новые** запрещённые импорты, новые исполняемые import cycles, и отсутствие новых domain-layer leaks. Исключения не означают закрытый технический долг.

## ARCH-P2 — сквозная инвалидация и authoritative facts

В `frontend/src/App.tsx:1842-1845` есть подписка `subscribeProgressMutation`, которая инвалидирует весь перечень `participantProjectionKeys` после covered mutation. `bootcamp/catalog.tsx` также инвалидирует собственные keys. Это реальный механизм обновления, но он требует измерения дублирующих refetch, отсутствующих keys и гонок при смене роли/двух параллельных запросах.

Сервер остаётся источником истины для `finished`, `verified`, `career grade`, `Skill Passport`, `rating`, `accepted contribution` и `consent`. Нельзя выводить подтверждённую компетенцию/баллы/грейд из одного client-side `finished`.

## Alembic и CI

Обнаружены 33 миграции с одной головой и без отсутствующих parent revisions в статическом графе. Это **не доказывает**, что миграции реально применяются на PostgreSQL и корректно откатываются — для этого нужен отдельный integration job.

В основном CI уже определены OpenSpec strict, Ruff/Pyright, PostgreSQL migration + pytest, ESLint/TS/Vitest, frontend build + Playwright, Docker smoke и security scans. При активных одновременных коммитах часть workflow runs отменяется по `cancel-in-progress: true`; отсутствие успешного полного gate на закреплённой integration revision нельзя трактовать как успех.
