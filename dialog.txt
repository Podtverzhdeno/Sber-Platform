Я бы принял **смену центра продукта**: основной результат Impulse — не прохождение обучения, а подтверждённое соответствие человека потребности команды. При этом предложение Златы и ответ Вадима хорошо сочетаются. Обучение готовит к практике; реальные задачи дают доказательства; руководитель использует их для отбора.

Сценарий руководителя я вижу так:

```text
Потребность команды
    → критерии нужных компетенций
    → кандидаты с проверенными доказательствами
    → приглашение выбранных людей на задачу
    → оценка их работы
    → интервью / кадровый резерв / решение о найме
```

Это близко к связке проектов и кадрового резерва у [Riipen](https://www.riipen.com/product/employers). [Forage](https://www.theforage.com/) полезен как пример коротких рабочих симуляций, а [CodeSignal](https://support.codesignal.com/hc/en-us/articles/22112130416535-Quick-Start-Guide-Assessments) — как пример переносимого результата оценки навыков. Для Impulse самое ценное отличие могло бы быть в **цепочке доказательств**: руководитель видит не один балл, а задачу, личный вклад, артефакт, критерии и подписанную человеком оценку.

В текущей SDD для этого уже есть основа: задачи и вклады, компетенции, портфолио, роли заказчика и руководителя, HR-воронка, согласия на доступ. Главный новый продуктовый сценарий — **закрытая задача по приглашению выбранных кандидатов**. Здесь нужно явно определить, кто видит задачу, может ли приглашённый отказаться, сколько кандидатов допускается и как руководитель сравнивает результаты по одной рубрике. Права заказчика можно дать руководителю на *его собственную задачу*; отдельную роль ради этого вводить необязательно.

Рейтинг я бы сохранил как добровольную мотивацию участника. Для руководителя «топ-10» лучше строить **под конкретный запрос** и показывать причины попадания в подборку: подтверждённые навыки, похожие работы, актуальность доказательств. Общий рейтинг не отвечает на вопрос, кто лучше решит именно эту задачу. Символическую премию за 5+ тоже можно оставить отдельной гипотезой пилота; её следует оценивать отдельно от качества отбора и не смешивать с обещанием трудоустройства.

Для 12-недельного пилота я бы сделал главным показателем не число сертификатов, а цепочку: **подтверждённая компетенция → интерес руководителя → приглашение на кейс → интервью**. «Экономию времени» стоит измерять сравнением времени руководителя на отбор, иначе это останется красивым, но недоказанным тезисом.

Пока это продуктовая гипотеза и моя рекомендация, не принятое решение: SDD и код я не менял.

[ПОЛЬЗОВАТЕЛЬ]
и не забудь про Роль Заказчик — общая логика
Заказчик в Impulse — это представитель команды / бизнеса / R&D-направления, который приходит на платформу не учиться и не менторить, а чтобы:
- поставить реальную задачу;
- привлечь сильных участников;
- получить практический результат;
- отобрать подходящих исполнителей;
- отслеживать прогресс;
- принимать или возвращать результат;
- анализировать эффективность своих задач;
- повторно использовать сильных участников и удачные форматы.
То есть основной путь заказчика такой:
идея / проблема → создание задачи → сбор заявок → отбор участников → работа → результат → приёмка → аналитика / повторное использование
1. Главная
Это стартовый дашборд заказчика.
Он нужен, чтобы сразу увидеть состояние всех задач и результатов без погружения в детали.
Что отображается
1) Верхние KPI-карточки
Показываются базовые показатели по задачам:
- Опубликовано — сколько задач опубликовано;
- В работе — сколько задач сейчас выполняются;
- На проверке — сколько результатов ожидают решения заказчика;
- Принято — сколько результатов уже успешно принято.
Продуктовый смысл
Эти карточки дают заказчику мгновенное понимание:
- насколько активен его контур;
- сколько задач реально движутся;
- есть ли “узкое место” на стадии проверки;
- насколько платформа даёт практический output.
2) Ближайшая задача под контролем
Большой центральный блок с одной приоритетной задачей.
Обычно в нём видно:
- тип задачи (например MVP / R&D);
- ID;
- название;
- краткое описание;
- статус;
- сколько заявок;
- сколько участников в работе;
- дедлайн;
- кнопки:
  - Открыть задачу
  - Посмотреть результаты
Что это значит
Система подсказывает заказчику:
«Вот задача, которая сейчас важнее всего и требует внимания».

Это помогает не искать вручную среди десятков карточек.
3) AI-помощник заказчика
Отдельный виджет с ролью AI.
Он помогает:
- формулировать ТЗ;
- улучшать ясность постановки;
- предлагать формат работы;
- анализировать похожие задачи;
- рекомендовать оптимальные условия.
Также важно, что в интерфейсе подчёркнуто ограничение:
- AI не публикует задачу;
- AI не принимает решения об оплате;
- AI не заменяет заказчика.
Смысл
AI — это не “автоматический менеджер”, а интеллектуальный ассистент для ускорения и повышения качества постановки задач.
4) Мои задачи
Список задач заказчика в нижней части.
Обычно видны:
- название;
- тип / теги;
- статус;
- число заявок;
- дедлайн;
- диапазон вознаграждения.
Есть быстрые переключатели:
- все;
- в работе;
- на проверке;
- завершённые.
Зачем это нужно
Это основной рабочий short-list:
- быстро перейти к задаче;
- увидеть просрочки;
- понять, где мало откликов;
- сравнить активность по задачам.
5) Последние результаты
Блок с последними присланными результатами:
- название результата;
- автор;
- статус (например принят / на проверке);
- дата;
- сумма / ценность результата.
Смысл
Заказчик видит не только задачи, но и практические выходы, которые уже поступают.
6) Ключевая аналитика
Небольшой summary-блок:
- среднее время до результата;
- доля принятых результатов;
- активные участники.
Зачем
Это мини-аналитика прямо на главной:
- показывает качество воронки;
- помогает быстро оценивать эффективность платформы.
Главная функция раздела
Главная заказчика = executive dashboard, где он сразу видит:
- сколько задач живут;
- сколько результатов поступило;
- какая задача сейчас самая важная;
- насколько эффективно работает весь контур.
2. Мои задачи и результаты
Это основной операционный раздел заказчика, где сосредоточены все его задачи.
Что отображается
1) Верхние статусы
Повторяются ключевые состояния:
- опубликовано;
- в работе;
- на проверке;
- принято.
Смысл
Это быстрый срез по всей воронке задач.
2) Фильтрация по типам задач
Есть вкладки / фильтры:
- все;
- в работе;
- на проверке;
- завершённые;
- черновики.
Что даёт
Заказчик может отдельно работать:
- с активными задачами;
- с незавершёнными черновиками;
- с задачами, где уже есть результаты;
- с теми, которые нужно срочно проверить.
3) Таблица задач
Для каждой задачи обычно показаны:
- название;
- теги / направления;
- статус;
- число заявок;
- число участников;
- дедлайн;
- лучший результат / лучший бюджетный outcome.
Зачем
Это уже не просто список, а рабочий task portfolio, где удобно:
- сравнивать задачи между собой;
- сортировать;
- оценивать интерес участников;
- видеть, где задача “не полетела”, а где получился сильный отклик.
4) Правая карточка выбранной задачи
При выборе задачи справа открывается подробный summary.
Часто там видны:
Основная информация
- проблема;
- ожидаемый результат;
- критерии оценки;
- дедлайн;
- модель поддержки;
- призовые места / схема компенсации;
- версия условий.
Последний результат от участника
- кто сдал;
- рейтинг;
- короткое описание результата;
- демо;
- презентация;
- репозиторий;
- иные артефакты.
Смысл
Это помогает заказчику быстро оценить задачу и последний outcome без перехода на отдельную страницу.
Главная функция раздела
Мои задачи и результаты = основное рабочее пространство заказчика, где он:
- управляет портфелем задач;
- следит за их состоянием;
- просматривает поступающие результаты;
- сравнивает эффективность разных задач.
3. Создать задачу
Это один из ключевых экранов для заказчика — место, где он формирует задачу для платформы.
Общая логика экрана
Экран построен как пошаговый wizard, чтобы заказчик не просто “написал текст”, а создал качественный, структурированный бриф.
Этапы на макете:
1. Бриф
2. Критерии и сроки
3. Условия и оплата
4. Поддержка
5. Проверка и публикация
Это очень хорошая логика, потому что разбивает сложную постановку задачи на понятные блоки.
Что входит в раздел
1) Название задачи
Краткое и понятное название.
Смысл
Нужно для:
- привлечения релевантных участников;
- поиска;
- первичного понимания темы задачи.
2) Тип задачи
Например:
- R&D
- MVP
- Исследование
Что это даёт
Позволяет сразу обозначить формат работы:
- эксперимент;
- прототип;
- аналитика;
- сравнение решений;
- прикладная разработка.
Это влияет и на ожидания участника, и на модель проверки.
3) Направления
Например:
- AI / ML;
- NLP;
- научные публикации и т.д.
Смысл
Используется для:
- рекомендаций участникам;
- точного матчинга;
- аналитики;
- структурирования контента платформы.
4) Проблематика и цель
Это один из важнейших блоков.
Здесь заказчик описывает:
- в чём реальная проблема;
- почему задача важна;
- что нужно улучшить / проверить / исследовать;
- какой бизнесовый или исследовательский контекст.
Продуктовый смысл
Участник должен понимать не только “что делать”, но и зачем это делать.
5) Ожидаемый результат
Чёткое описание deliverable:
- рабочий прототип;
- API;
- демо;
- документация;
- инструкция по развёртыванию;
- аналитический отчёт;
- презентация и т.д.
Почему это важно
Это снижает риск рассинхронизации между:
- ожиданиями заказчика;
- пониманием участника;
- будущей приёмкой результата.
6) Критерии успешности
Измеримые критерии:
- точность модели;
- покрытие;
- latency;
- готовность документации;
- наличие воспроизводимости и т.д.
Зачем
Без критериев участнику трудно понять “что считается хорошим результатом”, а заказчику — справедливо принимать работу.
7) Срок выполнения
Явный дедлайн.
Смысл
Нужен для:
- планирования;
- фильтрации по возможностям участников;
- SLA платформы;
- понимания срочности.
8) Количество мест
Сколько участников / команд могут быть отобраны.
Зачем
Поддерживает разные модели:
- один исполнитель;
- несколько исполнителей;
- соревновательный формат;
- parallel exploration.
9) Данные и интеллектуальная собственность
Отдельный блок про:
- какие данные предоставляет заказчик;
- открытые или закрытые датасеты;
- кому принадлежат результаты;
- что остаётся у заказчика.
Это критически важно
Потому что задачи могут быть:
- учебные;
- исследовательские;
- прикладные;
- корпоративные,
  и у них разные требования к IP.
10) Формат задачи
Например:
- платная;
- неплатная / исследовательская / образовательная.
Смысл
От формата зависит мотивация и ожидания участников.
11) Условия оплаты
Очень важный блок.
Показываются:
- базовый уровень;
- повышенный уровень;
- максимальный уровень / выдающийся результат.
Что это даёт
Это делает модель компенсации:
- прозрачной;
- мотивирующей;
- заранее зафиксированной.
12) AI-помощник заказчика
Блок рекомендаций:
- добавить целевую аудиторию;
- уточнить формат данных;
- указать use cases;
- сделать бриф точнее.
Смысл
AI помогает улучшить постановку ещё до публикации.
13) Финальные действия
Кнопки:
- сохранить черновик;
- предпросмотр;
- опубликовать задачу.
Логика
Заказчик может:
- не публиковать сразу;
- сначала проверить;
- подготовить несколько версий;
- вернуться позже.
Главная функция раздела
Создать задачу = конструктор качественного брифа, который помогает заказчику превратить проблему в понятную, проверяемую и привлекательную задачу для исполнителей.
4. Заявки на задачу
Это раздел отбора участников на конкретную задачу.
Что отображается
1) Верхние метрики по заявкам
Показываются:
- всего заявок;
- отобрано в шорт-лист;
- назначено;
- в листе ожидания.
Смысл
Это аналог recruitment funnel, только для задачи.
2) Таблица заявок участников
Список кандидатов, где видно:
- имя;
- вуз / направление;
- выбранные направления;
- проекты;
- принятые вклады;
- оценки 5+;
- трофеи;
- курсы;
- match;
- статус.
Что это даёт
Заказчик может сравнивать кандидатов не только по “красивому профилю”, но и по подтверждённому опыту.
3) Фильтры
Можно фильтровать по:
- направлению;
- уровню;
- подтверждённым вкладам;
- оценкам 5+;
- курсам;
- трофеям и т.п.
Зачем
Позволяет быстро сузить список до релевантных участников.
4) Профиль участника справа
Правая карточка показывает:
О себе
Краткое описание экспертизы.
Подтверждённый вклад
То есть реальный опыт в похожей задаче.
Оценка 5+
Показатель качества прошлых вкладов.
Курсы
Что прошёл участник.
Трофеи
Внешние и внутренние достижения.
Match
Насколько профиль подходит задаче.
Что можно делать
- открыть полный профиль;
- пригласить;
- назначить.
5) Важное продуктовое значение
Этот экран очень хорошо поддерживает вашу идею:
заказчик выбирает не просто “студента по резюме”, а человека по подтверждённым evidence.

Главная функция раздела
Заявки = система отбора и shortlisting, где заказчик:
- сравнивает участников;
- оценивает их релевантность;
- принимает кадровое решение по задаче.
5. Результат по задаче / экран приёмки
Это критически важный экран, потому что именно здесь заказчик превращает “работу в процессе” в принятый или отклонённый результат.
Что отображается
1) Ход выполнения задачи
Сверху — визуальный pipeline:
- бриф;
- работа;
- сдача результата;
- ревью;
- приёмка;
- выплата.
Смысл
Заказчик видит весь lifecycle задачи и точку, в которой он сейчас находится.
2) Информация о задаче
Показываются:
- теги;
- статус;
- количество участников;
- количество результатов.
3) Вкладка “Результат”
Центральный контент страницы.
Есть:
- участник;
- сообщение от участника;
- дата сдачи;
- артефакты;
- комментарии;
- история.
4) Предоставленные артефакты
Например:
- PDF-отчёт;
- Jupyter notebook;
- презентация;
- ссылка на демо.
Что это даёт
Заказчик видит не “один файл”, а комплект deliverables.
5) Соответствие ожидаемому результату
Очень полезный checklist:
- рабочий прототип;
- код и инструкции;
- исследовательский отчёт;
- презентация;
- демо / доступ;
- необязательные дополнения.
Почему это важно
Это делает приёмку:
- прозрачной;
- формализованной;
- справедливой.
6) Комментарии к результату
Показаны комментарии:
- от ментора;
- от заказчика;
- возможно история обсуждения.
Продуктовый смысл
Заказчик принимает решение не “в вакууме”, а с контекстом:
- внутренний review;
- замечания;
- уточнения;
- история изменений.
7) Правая панель — условия задачи
Здесь фиксируется immutable-версия условий:
- тип задачи;
- направление;
- дедлайн;
- бюджет;
- формат работы;
- уровень исполнителя;
- полное ТЗ.
Это очень правильное решение
Потому что на момент приёмки заказчик смотрит результат относительно зафиксированной версии условий, а не по “воспоминаниям”.
8) Вознаграждение участника
Показаны уровни выплаты:
- базовая;
- повышенная / A / B уровни и т.д.
Смысл
Решение заказчика по качеству результата связано с прозрачной моделью выплаты.
9) Блок “Ваше решение”
Финальные действия:
- принять результат;
- вернуть на доработку;
- открыть спор.
Это один из главных процессных блоков
Он запускает:
- изменение статуса;
- дальнейшую проверку;
- начисление;

Главная функция раздела

Коротко: продуктовая суть роли заказчика
Роль заказчика у вас состоит из 5 больших контуров.
1. Task publishing contour
- создание задачи;
- публикация;
- условия;
- критерии;
- оплата.
2. Selection contour
- заявки;
- short-list;
- назначение;
- база участников;
- приглашения.
3. Execution contour
- отслеживание задач;
- коммуникация;
- ход работы;
- промежуточный контроль.
4. Acceptance contour
- просмотр результатов;
- сравнение с ТЗ;
- принятие / доработка / спор;
- решение о выплате.
5. Optimization contour
- аналитика;
- AI-инсайты;
- повторное использование сильных участников;
- улучшение формулировок и процессов.
Что особенно сильного в этой роли
Из того, что видно по вашим макетам, у роли заказчика особенно сильны следующие идеи:
1. Заказчик работает не “вручную”, а в прозрачной воронке
От создания задачи до приёмки всё структурировано.
2. Есть упор на подтверждённый опыт участников
Это очень важное отличие от обычных freelance / contest-схем.
3. Условия и выплаты фиксируются как версия задачи
Это снижает конфликты.
4. AI встроен как помощник, но не забирает полномочия
Очень правильный баланс.
5. Есть аналитика не только по задачам, но и по качеству контура
То есть заказчик может улучшать не одну задачу, а весь свой подход.   что-то может быть лишнее. Сначала в спеку занеси

2. сохранить существующие маршруты, API, данные, действия и бизнес-сценарии;
3. НЕ удалять функциональные возможности;
4. НЕ придумывать новую бизнес-логику без необходимости;
5. полностью переделать визуальную композицию экранов;
6. привести весь кабинет заказчика к дизайн-языку приложенных эталонных экранов участника;
7. использовать эталонные изображения как VISUAL SOURCE OF TRUTH.

Текущие скриншоты заказчика считать BEFORE STATE:

==================================================
2. ОБЩИЙ ДИЗАЙН IMPULSE
==================================================

Интерфейс должен восприниматься как premium dark enterprise product.

Основной характер:

- современный;
- технологичный;
- строгий;
- корпоративный;
- немного футуристичный;
- визуально насыщенный, но не перегруженный;
- никакого ощущения Bootstrap admin panel;
- никакого ощущения сырого MVP.

Фон:
глубокий navy / blue-black.

Не использовать чистый #000 как основной фон.

Визуально должны существовать как минимум уровни:

1. page background;
2. surface/card background;
3. highlighted/selected surface;
4. secondary nested surface.

Карточки:
- тонкая холодная граница;
- мягкий radius;
- иногда очень лёгкий cyan/blue glow;
- никакого тяжёлого shadow;
- никаких белых карточек.

Accent:
cyan / turquoise.

Secondary accent:
blue / indigo / violet.

Warning:
amber/orange.

Danger:
red.

Success:
cyan-green / emerald.

Primary CTA:
яркий turquoise/cyan с возможным мягким переходом в blue.

Secondary CTA:
dark background + border.

22. IMPLEMENTATION STRATEGY
==================================================

Перед изменением кода:

1. изучи текущую архитектуру frontend;
2. найди все маршруты заказчика;
3. составь список существующих функций по каждому экрану;
4. найди переиспользуемые компоненты участника;
5. найди существующие design tokens;
6. максимально переиспользуй их.

Если участник и заказчик сейчас используют разные UI primitives —
унифицируй их.

Сначала создай:
- shared design tokens;
- shared cards;
- shared controls;
- shared table components;
- shared layout.

После этого переделывай страницы.
